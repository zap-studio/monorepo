# AGENTS.md

Zap Studio monorepo: type-safe, framework-agnostic, composable, tree-shakeable TypeScript libraries published to npm and JSR.

## Layout

- `packages/*` — the published libraries (`fetch`, `react-hooks`, `monads`, etc. — see the root `README.md` for the current list).
- `apps/docs` — the [zapstudio.dev](https://www.zapstudio.dev) documentation site (Vocs, deployed to Cloudflare via Wrangler).
- `configs/*` — private shared configs: tsconfig bases (`@zap-studio/typescript`) and the shared `tsdown` build config.

pnpm workspaces, pnpm >= 12, Node 24 in CI. Dependency versions live in the workspace **catalog** — never pin a version in a package's `package.json`, use `"catalog:"`. Internal deps use `"workspace:*"`.

## Commands

Root `package.json` `scripts` is the source of truth; the ones worth knowing:

- `pnpm run publish:check` — the full gate (format check, typecheck, lint, fallow, test, build). Run this before calling a change done, or at minimum typecheck + lint + the affected tests, and report the real output.
- `pnpm run lint:fix`, `pnpm run format` — oxlint (type-aware) and oxfmt.
- `pnpm run test` — Vitest. Browser tests need Chromium once: `pnpm exec playwright install --with-deps chromium`.
- `pnpm run fallow` — unused dependency/export detection.
- `pnpm run react-doctor` — React-specific audit (`--scope full`); run it after touching `packages/react-hooks`. Not part of `publish:check`.

Scope work to one workspace with `pnpm --filter <name> ...`. Vitest is root-configured, so filter tests by path instead: `pnpm run test packages/react-hooks`.

## Package anatomy

Each `packages/<name>` has `src/`, `package.json`, `jsr.json`, `tsconfig.json`, `CHANGELOG.md`, `README.md`, `LICENSE`.

- `tsconfig.json` extends `@zap-studio/typescript/library.json` (or `react.json`). Both enable `isolatedDeclarations`, so **every exported symbol needs an explicit return/annotation type** — no inferred public types.
- `package.json` `exports` and the `dist` output are generated by `tsdown` (`configs/tsdown/tsdown.config.ts`). Do not hand-edit the `exports` map; add a source file and rebuild.
- Files matching `src/**/_*.ts` are private helpers, excluded from the build entry glob. Use the `_` prefix for anything not part of the public API.
- `jsr.json` mirrors `package.json`: its `version` must stay in sync and its `exports` point at `src/*.ts`, not `dist`. Bump both together.
- Packages are ESM-only, `"sideEffects": false`, `platform: "neutral"`. Keep them free of Node built-ins unless the package is explicitly Node-targeted; `node:` imports are never bundled.

## Code style

- TypeScript strict, plus the extra safety flags in `configs/typescript/base.json` (`exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, etc.).
- Relative imports carry the `.ts` extension (`./use-counter.ts`) — `allowImportingTsExtensions` is on and JSR requires it.
- `import type` for type-only imports (`verbatimModuleSyntax`).
- Arrow-function consts for exported functions and hooks, kebab-case file names, `use-*.ts` for React hooks.
- Formatting and import order come from oxfmt, lint rules from `@zap-studio/oxlint`. Don't fight them — run `pnpm run format` and `pnpm run lint:fix`. Lefthook runs both on staged files pre-commit.
- TSDoc on every exported symbol; the package entry point carries a `@module` block. Write what the thing does and the non-obvious constraint, not a restatement of the signature.
- Disable a lint rule inline only with a reason: `// oxlint-disable <rule> -- why`. The reason says why the rule does not fit here, not what the rule does.

## Language

Write everything in simple English (around B1 level): code comments, TSDoc, docs pages, README files, changelog entries, commit messages, PR text, and chat replies.

- Use common words and short sentences. One idea per sentence.
- Prefer "start" over "commence", "fix" over "remediate", "let" over "facilitate".
- Avoid idioms and rare phrasal verbs.
- Keep technical terms, API names, code, and error strings exactly as they are — do not simplify those.

This also applies to lint-disable reasons and any other inline note.

## Tests

Vitest runs two projects, selected purely by file name:

- `*.node.test.ts` — Node environment. For React hooks this is the SSR check (`renderToString`).
- `*.browser.test.ts` — real Chromium via Playwright. Use `@testing-library/react` (`renderHook`, `act`) for hooks, and real DOM/Web APIs.

Colocate tests next to the source file. `globals: true` and `restoreMocks: true` are set. Any behavior change needs a test in the matching project; a React hook generally needs both files.

## Docs

User-facing API or behavior changes ship with docs in the same change:

- Page content in `apps/docs/src/pages/<package>/*.mdx`.
- New pages must also be registered in the sidebar/topNav in `apps/docs/vocs.config.ts`.
- Update the package `README.md` too, and the root `README.md` when adding or removing a package.

## Changelogs and versioning

Every published package keeps a Keep a Changelog–style `CHANGELOG.md` and follows semver. Add an entry under the right heading (`Added` / `Changed` / `Fixed` / `Removed`) for anything user-visible, and bump both `package.json` and `jsr.json` versions in the same change.

## Commits and PRs

Conventional Commits, lowercase, imperative, short subject: `feat: add useBrowserEngine hook`, `fix: rework cookie types`. Branch off `main`; never commit straight to `main`. PRs state what changed, why, how it was validated, and whether it is breaking. Keep changes focused — no unrelated refactors. See `.github/CONTRIBUTING.md`.

## Gotchas

- `.github/CONTRIBUTING.md` mentions `pnpm run check`; that script does not exist. The real gate is `pnpm run publish:check`.
- `coverage/` and `dist/` are build output — never edit or commit fixes into them.
- Adding a dependency means adding it to the catalog in `pnpm-workspace.yaml` first, then referencing `"catalog:"`.
- `pnpm run fallow` fails on unused deps and exports; genuine false positives go in `.fallowrc.json`, not into a disabled check.
- A few paths are deliberately excluded from lint/build globs (see `oxlint.config.ts`, `.fallowrc.json`, the tsdown config) — check those before assuming a file is unlinted by accident.
