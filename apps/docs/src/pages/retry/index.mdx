# @zap-studio/retry

`@zap-studio/retry` gives you reusable retry policies and a built-in runner so you can add resilient retries to async operations without rewriting orchestration loops.

## Why retry?

Most hand-rolled retry implementations duplicate the same logic:

- track attempt counts
- catch errors
- calculate the next delay
- sleep between attempts
- throw a final terminal error

`@zap-studio/retry` centralizes that flow in policy classes. You pick (or write) a policy and pass your work to `policy.run(...)`.

## Features

- **Built-in policies**: [`FixedDelay`](/retry/fixed-delay) and [`ExponentialBackoff`](/retry/exponential-backoff).
- **A shared runner** via `BaseRetryPolicy.run(...)` with attempt-aware callbacks and custom sleep injection.
- **Structured terminal errors** through [`RetryError` and `AbortError`](/retry/retry-error).
- **Non-throw mode** (`throwOnExhausted: false`) for callers that prefer result objects over exceptions.
- **Cancellation** through [`AbortSignal`](/retry/abort-signal), checked before, between, and during retries.
- **Custom policy contracts** via [`BaseRetryPolicy` and the `RetryPolicy` type](/retry/custom-policies).

## Quick Example

```ts
import { ExponentialBackoff } from "@zap-studio/retry/exponential-backoff";

const policy = new ExponentialBackoff({
  maxAttempts: 5,
  baseDelayMs: 100,
  maxDelayMs: 2_000,
});

const users = await policy.run(async () => {
  const response = await fetch("https://api.example.com/users");
  if (!response.ok) {
    throw new Error(`Request failed with status ${response.status}`);
  }
  return await response.json();
});
```

If all five attempts fail, `run(...)` throws a `RetryError` carrying the attempt count and the last error.

## Core Concepts

- A **policy** decides _if_ and _when_ to retry through `next(...)`.
- The **runner** (`run(...)`) executes attempts, catches failures, sleeps, and stops.
- The **terminal error** is built by `onExhausted(...)` — a `RetryError` by default.
